  ---
  2. Agent 设计

  2.1 Agent 基类（app/agents/base.py）

  所有 Agent 共享的基础结构：

  BaseAgent:
    ├── name: str                          # Agent 标识
    ├── description: str                   # Supervisor 路由时的参考
    ├── system_prompt: str                 # 该 Agent 的角色提示词
    ├── tools: list[BaseTool]              # 该 Agent 可调用的工具列表
    ├── model: ChatOpenAI                  # LLM 实例（bind_tools 后）
    │
    └── run(state: TripState) → dict       # 执行入口（ReAct 循环）
         ├── 构造 messages (system + history + current)
         ├── model.invoke(messages)        # LLM 决策：思考 or 调工具
         ├── 如果是 tool_call → 执行工具 → 结果追加到 messages → 循环
         └── 如果是 final_answer → 提取结果 → 写入 state → 返回

  关键设计决定：每个 Agent 使用 ReAct + Tool Calling 模式（而非简单的 function call）——Agent 的 LLM
  自主决定是否调用工具、调用哪个工具、调用几次。

  2.2 各 Agent 详细设计

  2.2.1 Supervisor Agent（监督者）

  ┌──────────┬───────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │   维度   │                                                 说明                                                  │
  ├──────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 职责     │ 全局编排器。分析当前状态，决定下一步应该激活哪个 Agent                                                │
  ├──────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 输入     │ 完整的 TripState（含 request、已收集的数据、phase、error、retry_count）                               │
  ├──────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 输出     │ next_agent 路由信号（"poi" / "weather" / "hotel" / "planner" / "budget" / "finalize" / "END")         │
  ├──────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 决策逻辑 │ LLM 调用，SystemPrompt 包含完整的决策规则（后面详述）                                                 │
  ├──────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 工具     │ 无工具。Supervisor 自己不调外部 API，只做路由决策                                                     │
  ├──────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 失败处理 │ 如果某个 Agent 失败，Supervisor 可以：①重试（retry_count <                                            │
  │          │ 3），②跳过该步骤（如果数据非必需），③降级（使用常识替代）                                             │
  └──────────┴───────────────────────────────────────────────────────────────────────────────────────────────────────┘

  Supervisor 决策规则（SystemPrompt 核心）：

  你是旅行规划的总监督者。你需要根据当前状态决定下一步行动。

  决策规则（按优先级）：
  1. 如果 raw_attractions 为空 → next_agent = "poi"
  2. 如果 raw_weather 为空 → next_agent = "weather"
  3. 如果 raw_hotels 为空 → next_agent = "hotel"
  4. 如果以上数据已收集但 raw_plan_text 为空 → next_agent = "planner"
  5. 如果 trip_plan 已生成但 budget 未计算 → next_agent = "budget"
  6. 如果以上全部完成 → next_agent = "finalize"
  7. 如果某个 Agent 失败且 retry_count < 3 → 重试该 Agent
  8. 如果某个 Agent 失败且 retry_count >= 3 → 跳过，用常识降级
  9. 如果 budget 超限 → 返回 planner 重新规划
  10. 如果 planner 生成的景点与搜索到的景点不匹配 → 返回 planner 修正

  为什么 Supervisor 要用 LLM 而不是 if-else？ 因为真实场景中决策树会非常复杂（预算超限回退、用户偏好冲突、API
  失败后的降级策略等），用 LLM 做决策比硬编码 if-else 更灵活且可扩展。

  ┌────────┬────────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │  维度  │                                                  说明                                                  │
  ├────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 职责   │ 综合所有收集的数据，生成结构化旅行计划                                                                 │
  ├────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────┤

  与旧架构的关键区别：
  - 旧：一个 prompt 生成所有内容，garbage in → garbage out
  - 新：Planner 有 validate 工具，可以自检并修正；有 search_missing_info 工具，缺数据时可以补搜而不是编造

  │ 工具    │ calculate_budget_tool: 汇总景点门票+酒店+餐饮+交通；suggest_savings_tool: LLM                         │
  │         │ 分析哪些景点可以替换为免费景点、哪些酒店可以降级                                                      │
  ├─────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ LLM     │ "你是旅行预算分析师。精确计算每笔费用，如果超限提供切实可行的削减方案。"                              │
  │ 角色    │                                                                                                       │
  ├─────────┼───────────────────────────────────────────────────────────────────────────────────────────────────────┤

  │ State   │                                                                                                       │
  └─────────┴───────────────────────────────────────────────────────────────────────────────────────────────────────┘

  为什么 Budget 要独立成 Agent？
  预算计算不是简单的加法——需要判断合理性（如"门票600元/人"是否离谱），需要与用户预算对比，需要给出削减建议。如果用
  Planner 一个 prompt 搞定，这些都会变成"拍脑袋"的数字。

  3. LangGraph 工作流设计

  3.1 节点划分

  ┌───────────────┬────────────┬──────────────────┬────────────────┐
  │     节点      │    类型    │    对应 Agent    │    是否 LLM    │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ initialize    │ 普通函数   │ 无               │ 否             │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ supervisor    │ Agent 节点 │ Supervisor Agent │ 是（路由决策） │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ poi_agent     │ Agent 节点 │ POI Agent        │ 是（ReAct）    │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ weather_agent │ Agent 节点 │ Weather Agent    │ 是（ReAct）    │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ hotel_agent   │ Agent 节点 │ Hotel Agent      │ 是（ReAct）    │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ planner_agent │ Agent 节点 │ Planner Agent    │ 是（ReAct）    │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ budget_agent  │ Agent 节点 │ Budget Agent     │ 是（ReAct）    │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ finalize      │ 普通函数   │ 无               │ 否             │
  ├───────────────┼────────────┼──────────────────┼────────────────┤
  │ handle_error  │ 普通函数   │ 无               │ 否             │
  └───────────────┴────────────┴──────────────────┴────────────────┘

  LLM 调用次数预期（以一次典型请求为例）：
  - Supervisor：3-7次（每次 Agent 返回后重新评估）
  - POI Agent：2-4次（策略分析 + 多轮搜索评估）
  - Weather Agent：2次（分析 + 确认）
  - Hotel Agent：2-4次（分析 + 搜索 + 筛选）
  - Planner Agent：3-5次（生成 + 自检 + 修正）
  - Budget Agent：2-3次（计算 + 分析 + 方案）
  - 总计：约 15-30 次 LLM 调用（对比旧架构的 1 次）

  3.2 条件分支设计

  # 新 routing.py 核心逻辑

  def supervisor_router(state: TripState) -> str:
      """
      根据 Supervisor 的决策，路由到下一个节点

      返回节点名称字符串，LangGraph 会据此执行 add_conditional_edges
      """
      next_agent = state.get("next_agent", "")

      # 如果 error 不为空且 retry_count < 3，重试同一 Agent
      if state.get("error") and state.get("retry_count", 0) < 3:
          return state.get("last_agent", "supervisor")

      # 如果 retry_count >= 3，跳过该步骤进入降级
      if state.get("error") and state.get("retry_count", 0) >= 3:
          return "supervisor"   # 让 Supervisor 重新决策

      # 正常路由
      route_map = {
          "poi": "poi_agent",
          "weather": "weather_agent",
          "hotel": "hotel_agent",
          "planner": "planner_agent",
          "budget": "budget_agent",
          "finalize": "finalize",
          "end": END,
      }
      return route_map.get(next_agent, "finalize")

  3.3 工作流图结构

  START
    │
    ▼
  initialize          ← 解析请求、初始化 messages、设置 phase
    │
    ▼
  supervisor          ← LLM 分析 State，输出 next_agent
    │
    ├─(next="poi")──────► poi_agent ──────► supervisor
    ├─(next="weather")──► weather_agent ──► supervisor
    ├─(next="hotel")────► hotel_agent ────► supervisor
    ├─(next="planner")──► planner_agent ──► supervisor
    ├─(next="budget")───► budget_agent ───► supervisor
    ├─(next="finalize")─► finalize ───────► END
    └─(next="end")──────► END

  关键约束：
  - 所有 Agent 节点执行完毕后强制返回 supervisor（不做任何其他路由）
  - Supervisor 是唯一的决策点——这避免了"面条式"的条件分支
  - 循环次数由 max_iterations 限制（建议设置为 20，防止无限循环）

  3.4 错误处理机制

  三层错误处理：

  ┌─────────────────────────────────────────────┐
  │ 层1：Agent 内部错误处理（ReAct 循环内）        │
  │   - 工具调用失败 → LLM 决定是否换参数重试      │
  │   - JSON 解析失败 → LLM 自行修正格式           │
  │   - 结果为空 → LLM 决定是否换策略补搜          │
  ├─────────────────────────────────────────────┤
  │ 层2：Supervisor 级错误处理                     │
  │   - Agent 最终失败 → 写入 error + retry_count │
  │   - retry_count < 3 → 重试同一 Agent          │
  │   - retry_count >= 3 → 降级（用常识/跳过）     │
  ├─────────────────────────────────────────────┤
  │ 层3：全局兜底（finalize 节点）                 │
  │   - trip_plan 为空 → _create_fallback_plan   │
  │   - budget 为空 → 简单估算                     │
  │   - 确保 API 总是返回可用的结果                 │
  └─────────────────────────────────────────────┘

  3.5 State 扩展

  class TripState(TypedDict):
      # ===== 原有字段 =====
      request: TripRequest
      raw_attractions: list[dict]
      raw_weather: list[dict]
      raw_hotels: list[dict]
      raw_plan_text: str
      attraction_photos: dict
      trip_plan: TripPlan | None
      error: str

      # ===== 新增字段 =====
      messages: list[BaseMessage]       # Agent 间共享的对话历史
      next_agent: str                   # Supervisor 的最近一次路由决策
      last_agent: str                   # 上一个执行的 Agent 名称
      retry_count: int                  # 当前步骤的重试次数
      phase: str                        # 当前阶段 ("collect" | "plan" | "review" | "done")
      max_iterations: int               # 全局最大迭代次数（默认 20）
      iteration_count: int              # 当前迭代次数
      agent_outputs: dict               # 各 Agent 的输出摘要（供 Supervisor 快速查阅）

  原建议: 前端伪进度条替换为真实进度
  本方案落实方式: 利用 LangGraph 的 streamEvents / astream_events，在 routes.py 中改为 SSE（Server-Sent

  5.4 条件分支错误处理（7.5-4）

  原建议: 利用 add_conditional_edges 增加错误处理分支
  本方案落实方式: 三层错误处理（见 3.4 节）：① Agent 内部 ReAct 自愈（换参数重试）② Supervisor
    级重试/降级（add_conditional_edges 中判断 error + retry_count）③ finalize
    节点全局兜底（_create_fallback_plan）具体路由：supervisor → routing_function → poi_agent | weather | hotel | planner

    | budget | finalize当 error 非空且 retry_count < 3：routing_function 返回 last_agent（重试）当 error 非空且
    retry_count >= 3：routing_function 返回 supervisor（降级再决策）

  5.5 拆分 plan_itinerary（7.5-5）

  原建议: 拆分 plan_itinerary 为多次 LLM 调用

    第1次：分析住宿偏好+预算 → 决定搜索策略• 第2-N次：评估 → 筛选/补搜Planner Agent（3-5次 LLM 调用）：• 第1次：综合数据

    → 生成行程 JSON• 第2次：调用 validate_itinerary_tool → 自检（JSON 格式/景点数量/日期连续性）• 第3-N次：如发现问题 →

    生成削减方案Supervisor（3-7次 LLM 调用）：• 每次 Agent 返回后重新决策
